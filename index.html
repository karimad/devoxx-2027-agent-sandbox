Un agent qui lance du code expose vos clés cloud

Code non fiable

L'agent écrit et lance du code que personne n'a relu.

Clés à portée

Le code tourne souvent là où se trouvent les credentials cloud.

Isolation lente

Un sandbox neuf par requête coûte 8 à 12 s de démarrage dans nos essais locaux.

Question du talk : comment isoler chaque requête sans la ralentir, et sans jamais confier de clé à l'appelant ?

L'agent atteint vos secrets par quatre chemins

Credentials cloud

Un token lisible par le code est une clé volée.

Réseau interne

Par défaut, aucune sortie vers les plages privées (RFC 1918).

Résidus entre requêtes

Ce qui survit au nettoyage d'un pod passe à la requête suivante.

Délégation

Qui agit pour qui, avec quels droits, et jusqu'à quand ?

Le chargement des credentials IRSA se teste sans compte AWS

Un exemple basé sur LocalStack, qui fonctionne sur n'importe quel cluster local.

Il vérifie que les pods du sandbox chargent leurs credentials comme sur AWS.

Limite : LocalStack simule AWS, il ne prouve pas l'authentification STS réelle.

Écart reproduit sur un pool de pods préchauffés réel (EKS Anywhere). Un nettoyage côté appelant le comble : vérifié.

Référence : KEP-539.2, spécification de Clean() dans agent-sandbox.

Des règles deny inopérantes laissaient tout passer

# schéma simplifié
deny if command contains "rm -rf"
Opérateur contains absent du DSL
La règle ne se déclenche jamais
L'action est autorisée

Correctif : contains, startswith et endswith ajoutés au DSL (PR #3924, mergée le 15 septembre 2026).

Le même schéma est revenu dans d'autres couches du même projet : callbacks et appels asynchrones.

Règle de conception : en cas d'erreur, bloquer

1

Une règle impossible à évaluer refuse l'action.

2

On teste le chemin d'erreur autant que le chemin nominal.

3

Chaque requête repart d'un état propre, sans credentials.
